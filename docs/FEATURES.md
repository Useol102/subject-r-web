# 기능 목록 (3단계)

> `docs/SCREEN-FLOW.md` 의 화면에서 뽑아낸 기능들이다.
> 각 기능에 **이름표**를 붙여 이후 단계(데이터 정의 → ERD → API → 구현)에서 추적한다.
>
> 이름표는 `역할-기능` 형태다. 커밋 메시지에 그대로 쓴다:
> `feat(직원-목적지편집): 숨김 시 진행중 안내 확인 추가`
>
> **상태 표기**
> ✅ 구현됨 · ⚠️ 일부만 · ❌ 없음 · ⏸ 외부 답변 대기 · 💤 이번 범위 아님

### 아직 인증이 없는 경로

| 경로 | 왜 열어뒀나 |
|---|---|
| `GET /maps/{id}/pois` | 어르신 키오스크는 로그인이 없다 |
| `POST /trips`, `PATCH /trips/{id}` | 키오스크가 안내를 요청·취소한다 |
| `GET /maps/{id}/bundle` | 로봇이 쓴다. **로봇 전용 인증이 아직 없다** |
| `GET /robots`, `GET /trips` | 대시보드와 로봇이 함께 쓴다 |

지금은 **LAN 안에서만 접근 가능하다는 전제**에 기대고 있다.
`로봇-상태보고` 를 만들 때 로봇 토큰(`robot.uuid` 기반)을 함께 도입한다.

## 이 표의 사용법

기능이 추가되거나 화면이 바뀌면 **여기부터 고친다.**
그다음 상태가 ❌ 인 줄을 보고 스키마·API를 만든다.

거꾸로, API를 새로 만들 때는 **어느 기능을 위한 것인지** 커밋 메시지에 적는다.

```
feat(직원-목적지편집): POI 편집 API 추가
fix(사용자-안내취소): 취소 시 ended_at 누락 수정
```

이러면 "이 API 왜 있지?" 를 나중에 추적할 수 있다.
1차 때 이게 없어서 요구분석과 대조가 안 됐다.
