# 기능 목록 (3단계)

> `docs/SCREEN-FLOW.md` 의 화면에서 뽑아낸 기능들이다.
> 각 기능에 **이름표**를 붙여 이후 단계(데이터 정의 → ERD → API → 구현)에서 추적한다.
>
> 이름표는 `역할-기능` 형태다. 커밋 메시지에 그대로 쓴다:
> `feat(직원-목적지편집): 숨김 시 진행중 안내 확인 추가`
>
> **상태 표기**
> ✅ 구현됨 · ⚠️ 일부만 · ❌ 없음 · ⏸ 외부 답변 대기 · 💤 이번 범위 아님

### 위치 데이터를 둘로 나눈 이유

| | 저장 방식 | 쓰임 | Hz 필요 |
|---|---|---|---|
| 최신 위치 1건 | `robot.last_geom` (덮어쓰기) | 대시보드 아이콘, 진행률 | ❌ |
| 위치 시계열 | `pose_log` (월 파티션, 3차) | 과거 궤적, 주행 통계 | ✅ |

이렇게 나눈 덕에 **시뮬팀 답변을 기다리지 않고** 어르신 진행 화면과
대시보드 로봇 위치를 먼저 만들 수 있었다.
`pose_log` 는 주기가 정해지면 별도로 추가한다 — 최신 위치 컬럼은 그때도 그대로 쓴다.

### 인증 구조

| 호출자 | 방법 | 접근 범위 |
|---|---|---|
| 어르신 키오스크 | `X-Robot-Key` (키오스크는 로봇 위에서 돈다) | 목적지 목록, 안내 요청·취소, 번들 |
| 로봇 | `X-Robot-Key` | 위 + `/robots/me`, 상태 보고, 사건 보고 |
| 직원 viewer | `Authorization: Bearer` | 조회 전반 |
| 직원 staff | 위 + 목적지·구역 편집 | |
| 관리자 admin | 위 + 계정 관리, 로봇 키 발급 | |

**인증 없이 열린 경로는 `/health` 와 `/auth/login` 둘뿐이다.**

로봇 키는 SHA-256으로 해싱해 저장한다. bcrypt를 쓰지 않는 이유는 두 가지다 —
로봇이 1Hz로 보고하면 요청마다 bcrypt를 돌리는 게 부담이고,
bcrypt는 salt가 매번 달라 해시로 바로 조회할 수 없어 전체 로봇을 순회해야 한다.
API 키는 우리가 만든 256비트 난수라 사전 공격 대상이 아니므로 느린 해시가 필요 없다.

## 이 표의 사용법

기능이 추가되거나 화면이 바뀌면 **여기부터 고친다.**
그다음 상태가 ❌ 인 줄을 보고 스키마·API를 만든다.

거꾸로, API를 새로 만들 때는 **어느 기능을 위한 것인지** 커밋 메시지에 적는다.

```
feat(직원-목적지편집): POI 편집 API 추가
fix(사용자-안내취소): 취소 시 ended_at 누락 수정
```

이러면 "이 API 왜 있지?" 를 나중에 추적할 수 있다.
1차 때 이게 없어서 요구분석과 대조가 안 됐다.
