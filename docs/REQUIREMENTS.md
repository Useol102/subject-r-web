# 요구분석 (초안)

> 회의에서 확정할 초안이다. **`[제안]` 은 웹팀 의견이고 아직 결정이 아니다.**
> `[확정]` 은 회의록이나 팀 합의로 이미 정해진 것.
>
> 확정되면 그에 맞춰 스키마와 API를 고친다. 스키마 변경은 Alembic 마이그레이션으로 하므로
> 이미 만든 것을 버리지 않고 수정할 수 있다.

---

## 0. 이 문서를 쓰는 이유

1차 스키마는 회의록의 로봇 기능 로드맵(①~⑨)에서 도출했다.
예를 들어 "⑤ 목적지 UI"에서 `poi` 테이블이, "⑦ 음성"에서 `voice_script` 컬럼이 나왔다.

문제는 **그 도출 과정을 아무도 볼 수 없었다는 것**이다.
그래서 "이 컬럼이 왜 있지?", "이 기능은 어느 테이블이 받지?" 를 확인할 방법이 없었다.

이 문서는 그 연결을 명시적으로 만든다. 실제로 이 작업을 하면서 **누락 4건**을 찾았다 (§6).

## 1. 누가 쓰는가

| 사용자 | 어디서 | 로그인 | 하는 일 |
|---|---|---|---|
| **어르신 / 방문자** | 로봇의 7인치 터치스크린 | `[제안]` **없음 (키오스크)** | 목적지 고르기, 안내 취소 |
| **복지관 직원** | PC 웹브라우저 | `[제안]` 있음 | 로봇 상태 확인, 안내 이력 조회, 목적지 관리 |
| **우리 팀 (개발/운영)** | PC 웹브라우저 | `[제안]` 있음 (admin) | 위 전부 + 지도 교체, 계정 관리 |

### `[제안]` 어르신에게 로그인을 시키지 않는 이유

- 회의록 ⑨ "노인 사용성 개선"과 정면으로 충돌한다. 아이디/비밀번호는 진입 장벽이다
- 개인정보를 안 받으면 동의 절차·보관 의무가 사라진다
- 누가 썼는지는 몰라도 **언제 어디로 몇 건** 안내했는지는 `trip`에 다 남는다

> **회의에서 확인할 것**: 복지관이 "누가 이용했는지" 기록을 원하는가?
> 원한다면 이름 입력 대신 **직원이 대신 요청**하는 방식을 제안한다 (`trip.requested_by = dashboard`).

### `[미결정]` 직원 웹은 어디까지 필요한가

9월 산출물이라 지금 확정할 필요는 없지만, 범위가 정해져야 화면 수가 나온다.

## 2. 사용자가 무엇을 할 수 있는가

### 2.1 어르신 — 로봇 터치스크린

```
[대기 화면]
    │  화면을 누름
    ▼
[목적지 선택]  큰 버튼 6~8개, 아이콘 + 짧은 글자
    │  버튼 누름
    ▼
[확인]  "화장실로 안내할까요?"  [네] [아니요]
    │  네
    ▼
[안내 중]  현재 위치, 남은 거리, 큰 [취소] 버튼
    │                          │
    │ 도착                     │ 취소 누름
    ▼                          ▼
[도착 안내]  음성 + 화면      [취소됨] → 대기 화면
    │  자동 5초 후
    ▼
[만족도]  얼굴 아이콘 3개 [좋아요/보통/불편해요]  (건너뛰기 가능)
    │
    ▼
[대기 화면]
```

`[미결정]` 굵게 표시한 부분들:

- **확인 화면이 필요한가?** 잘못 눌렀을 때 되돌릴 수단이 필요하지만 단계가 늘어난다
- **만족도를 물어볼 것인가?** ⑨ 사용성 개선의 데이터가 되지만, 어르신이 귀찮아할 수 있다
- **"도착 확인"을 누가 판정하는가?** 로봇이 좌표 도달로 자동 판정 / 사람이 버튼 누름

### 2.2 직원 — PC 웹

`[제안]` 9월 목표 기준 최소 세트

| 화면 | 하는 일 | 우선순위 |
|---|---|---|
| 대시보드 | 지도 위 로봇 실시간 위치, 배터리, 상태 | 높음 |
| 안내 이력 | 날짜별 trip 목록, 성공/실패, 소요시간 | 높음 |
| 목적지 관리 | POI 추가/수정/숨김, 음성 문구 편집 | 높음 |
| 구역 관리 | 진입금지·서행 구역 그리기 | 중간 |
| 지도 관리 | 새 SLAM 지도 업로드, 활성 버전 전환 | 중간 |
| 계정 관리 | 직원 계정 추가 | 낮음 |

## 3. 목적지를 어떻게 관리하는가

`[제안]` **관리자가 웹에서 추가·수정할 수 있어야 한다.** 코드에 하드코딩하지 않는다.

이유: 복지관은 프로그램실 용도가 바뀌거나 공사로 통로가 막힌다.
그때마다 개발자를 부르면 운영이 안 된다.

| 항목 | 목적지마다 관리할 값 | 왜 필요한가 |
|---|---|---|
| 이름 | `name_ko` "1층 화장실" | 이력·관리 화면용 |
| 짧은 이름 | `name_short` "화장실" | 7인치 화면 버튼용 |
| 분류 | `category` | 아이콘 결정, 목록 정렬 |
| 좌표 | `geom` (x, y) | 로봇이 갈 지점 |
| 도착 방향 | `approach_yaw` | 문 앞에서 벽 보고 서지 않게 |
| 음성 문구 | `voice_script` | ⑦ 음성 안내 |
| 휠체어 가능 | `wheelchair_accessible` | 안내 여부 판단 |
| 목록 노출 | `is_selectable` | 충전소는 좌표만 필요, 화면엔 안 뜸 |
| 사용 여부 | `is_active` | 공사 중이면 숨김. **삭제하지 않는다** |
| 정렬 순서 | `display_order` | 자주 쓰는 걸 위로 |

**삭제하지 않고 숨기는 이유**: 과거 `trip`이 그 목적지를 참조한다.
지우면 "지난달 화장실 안내 몇 건" 같은 통계가 깨진다.

`[미결정]` 목적지를 몇 개까지 보여줄 것인가.
7인치 화면에 큰 버튼이면 **한 화면에 6개** 정도가 한계다. 그보다 많으면 페이지 넘김이나
분류별 묶기가 필요한데, 노인 사용성에는 둘 다 좋지 않다. **실제 복지관 장소 수를 알아야 결정된다.**

## 4. 웹과 로봇이 무엇을 주고받는가

### 4.1 서버 → 로봇

| 언제 | 무엇 | 방식 |
|---|---|---|
| 로봇 부팅 / 지도 변경 | 지도 + 목적지 + 금지구역 + 경로 **한 번에** | `GET /maps/{id}/bundle` |
| 안내 요청 발생 | 목적지 좌표, 도착 방향 | trip 생성 시 |

**한 번에 받아가는 이유**: 복지관에 인터넷이 없다.
로봇은 이 묶음을 로컬에 저장해두고 오프라인으로 주행한다.

### 4.2 로봇 → 서버

| 언제 | 무엇 | 방식 |
|---|---|---|
| 주기적 | 현재 위치, 방향, 속도, 배터리 | `[미결정]` **주기(Hz) 미정** |
| 상태 변할 때 | 대기/주행중/충전중/오류/비상정지 | `PATCH /robots/{id}` |
| 사건 발생 시 | 장애물 감지, 재계획, 비상정지, 도착 | `POST /trips/{id}/events` |
| 인식했을 때 | 사람/휠체어/장애물 + 신뢰도 | `[미정]` 3차 |

`[미결정]` **위치 보고 주기.** 1Hz면 하루 8만 행, 10Hz면 80만 행이다.
대시보드에 부드럽게 보이려면 높아야 하고, 저장 부담은 낮아야 한다.
→ **제안: 저장은 1Hz, 화면 표시는 WebSocket으로 10Hz (저장 안 함)**

### 4.3 오류를 어떻게 알리는가

`[미결정]` 로봇이 길을 못 찾거나 배터리가 부족하면?

- 화면에 뭐라고 띄우는가 (어르신이 이해할 수 있는 말로)
- 직원을 어떻게 부르는가 (대시보드 알림? 소리?)
- 안내를 포기하고 원위치로 돌아가는가

## 5. 무엇을 기록하는가

### 5.1 안내 1건 (`trip`)

`[확정]` 이미 저장한다: 로봇, 지도, 모드, 상태, 출발지, 목적지, 요청 주체,
요청/시작/종료 시각, 계획 거리, 실제 거리, 실패 사유, 시뮬레이션 여부

### 5.2 주행 중 사건 (`trip_event`)

`[확정]` 시각 + 종류 + 심각도 + **좌표** + 상세(JSON)

좌표를 남기는 이유: "어느 지점에서 자꾸 막히나"를 지도에 찍을 수 있다.
⑨ 사용성 개선의 근거 데이터가 여기서 나온다.

### 5.3 `[제안]` 만족도 (`feedback`) — **아직 테이블이 없다**

| 컬럼 | 내용 |
|---|---|
| trip_id | 어느 안내에 대한 것인지 |
| rating | 1~5 또는 3단계 |
| comment | 자유 입력 (선택) |
| input_method | touch / voice |

**회의에서 확인할 것**: 만족도를 받을 것인가? 받는다면 몇 단계로?

### 5.4 개인정보 — **반드시 확인 필요**

`[미결정]` 로봇 카메라가 이용자 얼굴을 찍는다. 그 이미지를 저장하고 AI 학습에 쓰려면
**동의·고지 절차가 필요하다.**

지금 확인하지 않으면 10월 필드테스트에서 수집한 데이터를 아예 못 쓰게 될 수 있다.

웹팀 대비책: 저장 전 **얼굴 블러 처리**. 다만 이걸 하려면 파이프라인을 미리 설계해야 한다.

## 6. 지금 만든 것과 대조 — 발견한 누락

요구분석을 하면서 실제로 찾은 것들이다.

| 요구 | 현재 상태 | 판정 |
|---|---|---|
| 어르신이 목적지 선택 | `GET /maps/{id}/pois` | ✅ |
| 안내 시작 | `POST /trips` | ✅ |
| 안내 중 취소 | `PATCH /trips/{id}` → `canceled` | ✅ |
| 안내 기록 (시간/목적지/성공여부) | `trip` 테이블 | ✅ |
| 사건 기록 | `trip_event` | ✅ |
| 로봇 오프라인 동작 | `GET /maps/{id}/bundle` | ✅ |
| **관리자가 목적지 추가/수정** | 테이블은 있으나 **API 없음** | ❌ **누락** |
| **만족도 수집** | **테이블 자체가 없음** | ❌ **누락** |
| **직원 로그인** | `app_user` 테이블만 있고 **인증 API 없음** | ❌ **누락** |
| **로봇 실시간 위치** | `pose_log` 미구현, WebSocket 없음 | ❌ **누락 (3차 예정)** |

### 누락 4건에 대한 조치

| 누락 | 언제 | 비고 |
|---|---|---|
| POI 편집 API | 즉시 가능 | 테이블이 이미 있어 API만 추가 |
| `feedback` 테이블 | 회의 후 | 3단계인지 5단계인지 정해지면 |
| 인증 API | 즉시 가능 | `app_user`에 컬럼 다 있음 |
| 실시간 위치 | 주기(Hz) 확정 후 | 파티션 설계에 필요 |

> **`feedback` 테이블 누락은 이 요구분석이 없었으면 못 찾았을 것이다.**
> 원래 설계 문서에는 있었는데 1차 범위를 정하는 과정에서 조용히 빠졌다.

## 7. 회의에서 결정할 것 (우선순위)

| # | 질문 | 누가 답하나 | 막고 있는 것 |
|---|---|---|---|
| 1 | 어르신에게 로그인을 시킬 것인가 | 팀 + 복지관 | 계정 구조, 개인정보 절차 |
| 2 | 만족도를 받을 것인가, 몇 단계로 | 팀 | `feedback` 테이블 |

| 6 | 복지관 실제 장소명·층, **통로/엘리베이터 폭** | 임원 | 시드 데이터, 휠체어 경로 판정 |
| 7 | 직원 웹 화면 범위 | 팀 | 9월 작업량 |

## 8. 앞으로의 순서

```
[완료] 회의록 기능 로드맵 (①~⑨)
[완료] 1차 스키마 + API (초안)
[지금] 요구분석  ← 이 문서
   ↓
화면 흐름 확정 (와이어프레임)
   ↓
기능 목록 → 스키마·API 대조 → 수정
   ↓
9월 구현 (대시보드 / 사용자 UI)
```

1차 스키마를 버리지 않는 이유: 회의록의 기능 로드맵에서 도출했기 때문에
대부분은 그대로 쓴다. 바뀌는 부분은 **Alembic 마이그레이션으로 수정**한다.
그러려고 처음부터 마이그레이션 체계를 만들어뒀다.
